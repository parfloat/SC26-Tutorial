# fp16-divergence: nixnan catches TinyGPT's FP16 overflow, step by step

TinyGPT (`../tinygpt.py`, same data and initialisation as `../train.py`) is
trained entirely in FP16: parameters, activations and gradients, with no master
weights and no loss scaling. It uses plain SGD (momentum 0.9) at lr 1.0.

The run is deterministic. The loss rises from 2.53 to 649 over nine steps and is
NaN at step 10. Under nixnan the run is stopped (`watch_nan.py`) the moment
nixnan prints its first NaN report.

```
./run_nixnan.sh          # ~5 min: kernel names, two nixnan passes, summary, oracle
```

## The timeline nixnan reports (`logs/SUMMARY.txt`)

| step | loss | nixnan: largest magnitude at the FP16 residual add (`x + proj(…)`) | nixnan exceptions |
|---:|---:|---|---|
| 1–6 | 2.53 → 79.3 | below 2⁹ | none (subnormals only) |
| 7 | 169.9 | **2⁹** (≥ 512), `FFMA` | none |
| 8 | 198.8 | **2¹⁰** (≥ 1,024) | none |
| 9 | 649.4 | **2¹⁵** (≥ 32,768), 49,139 bin reports | none |
| 10 | — | 2¹⁵, then: | **±inf** in operands 0/1 of `FFMA R9, R9, c[0x0][0x164], R8` (add); then **±inf** in LayerNorm's `FADD R0, R19, -R16` (x − mean), then the first **NaN** in LayerNorm → **run killed** |

What this shows:

* **The inf is born in a GEMM and first seen at the residual add.** FP16's
  maximum is 65,504. Block 0's attention output projection (an FP16 cuBLAS GEMM,
  FP32 accumulate) produces values past it in step 10, and they round to ±inf.
  nixnan sees them as operands of the next kernel: the add
  `a + alpha·b` (`FFMA …, c[0x0][0x164]`, where `c[0x164]` is alpha).
* **The NaN is born in LayerNorm.** (Which LayerNorm instruction reports it first, the `x − mean` `FADD` or the `FFMA` after it, varies between runs. It depends on which warp reports first, and both are in the same kernel and step.) `x − mean` with x = ±inf and mean = ±inf
  gives inf − inf = NaN. After that, NaN spreads everywhere and the loss is NaN.
* **The build-up is visible three steps earlier.** The histogram bins show the
  residual stream crossing 512, 1,024 and 32,768 in steps 7, 8 and 9, each
  report naming the instruction.
* The FP16 bins never fire. PyTorch's elementwise and LayerNorm kernels convert
  FP16 to FP32 before computing, so nixnan sees these values as FP32 operands.
* LayerNorm's FP32 bins reach 2¹⁷ from step 6 on. Those are its sums of
  squares, which are FP32 and harmless.

The PyTorch-side oracle (`train_fp16.py --oracle`, `logs/oracle-lr1.txt`) agrees.
max |activation| goes 815 → 1,315 → 29,570 → 65,440 + 7,870 inf over steps 7–10.
The largest tensor is `blocks.0.proj`, and the first non-finite tensor is
`blocks.0.proj`'s output, at step 10.

## What it took (and what it shows about nixnan)

1. **Padding-lane false positives in healthy step 1.** Instrumenting everything,
   the first NaN report came in step 1, while every real tensor was finite.
   * It came from a CUTLASS GEMM's tensor-core operand
     (`logs/false-positive-gemm-step1.log`).
   * With GEMMs excluded, it came from PyTorch's warp softmax in
     `cross_entropy`, which pads each row with −inf so out-of-range rows compute
     −inf − (−inf) (`logs/false-positive-softmax-step1.log`).
   * This is the same effect as flash attention's padding lanes
     (`../PyTorch_Instrumentation/PyT.md`).
   * The exceptions pass therefore blacklists GEMMs, flash and the warp softmax
     (`blacklist.txt`). An overflow inside a GEMM still shows up, as an inf operand
     of the kernel that reads its output.
2. **`MAX_ERRORS=1` doesn't fit this case.** It stops at the first exception of
   any kind, and FP16 training produces subnormals immediately. `watch_nan.py`
   stops at the first NaN report instead.
3. **`HISTOGRAM` over all kernels crashes nixnan** (`logs/histogram-crash.log`).
   * Every FP instruction gets an entry in the instruction table, and
     `recorder::mk_entry` (`src/recording.cu:88`) writes
     `inst_info[current_entry++]` with no bounds check against `TABLE_SIZE`.
   * Large GEMM kernels overflow the table, the heap gets corrupted, and the run
     segfaults.
   * The histogram pass therefore whitelists two kernels.
4. **Function names.** nixnan cuts names at the first `<` or `(`, so
   anonymous-namespace kernels such as LayerNorm print as `void at::native::`.
   The kernel is identifiable only because the histogram pass instruments just
   two kernels.
